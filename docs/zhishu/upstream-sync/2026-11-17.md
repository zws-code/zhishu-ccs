## WorkBuddy：从二开实现切换到上游

| 方面 | 二开实现（已删除） | 现在 |
| --- | --- | --- |
| 代码 | `zhishu/integrations/ccswitch/workbuddy.rs`、`workbuddy_config.rs`、`src/zhishu/tools/workbuddy/` 及两组测试 | 上游 `src-tauri/src/workbuddy_config.rs`、`services/workbuddy_account/`、`commands/workbuddy_account.rs`、`WorkBuddyProviderForm.tsx` 等，字节级等同 v4.0.33 |
| 数据目录 | 设置覆盖 → `WORKBUDDY_CONFIG_DIR` → `~/.workbuddy` | `WORKBUDDY_CONFIG_DIR` → `~/.workbuddy`（上游 `workbuddy_config::data_dir()`）；设置页 WorkBuddy 目录覆盖不再提供 |
| 条目归属 | 以 url + apiKey 判断模型属于哪张卡 | 每个条目写 `ccSwitchProviderId`；无归属条目视为用户自建，只读不改；`availableModels` 白名单按上游规则增删 |
| 平台同步 | `{url: <root>/v1, apiKey, vendor, models[*].url/apiKey}` | `{vendor: "智枢平台", url: <root>/v1/chat/completions, apiKey, models: [...]}`；共享字段由上游 `set_provider` 复制进每个条目；旧行刷新时去掉条目内的 url/apiKey，避免覆盖共享字段 |
| 是否已安装 | 自有 `get_workbuddy_installed`（数据目录或 macOS 应用包） | 与上游应用页一致：`get_config_status("workbuddy").exists`（数据目录存在） |
| MCP / Skills | 二开禁用 | 采纳上游支持（schema 26 `enabled_workbuddy`） |

平台白名单（`platform_models.rs::AGENTS`、`platformConfig.ts::PLATFORM_SYNC_APPS`）仍含 `workbuddy`。同一模型 ID 在 WorkBuddy 中只能属于一张卡：两个平台分组含同名模型时，第二张卡在启用（写入 `models.json`）时会被上游以“同一个模型不能添加多次”拒绝并提示；平台同步本身只写数据库行，不受影响。这是上游的产品约束。

## 数据、安全与回退

- 主数据库 schema 25 → 26，仅新增默认关闭的 `enabled_workbuddy`；Provider、平台账号目录、keyring 会话不迁移。
- 已存在的二开 WorkBuddy 数据库行仍是 `app_type = "workbuddy"` 的供应商；平台托管行在下次本地同步时按新格式刷新。由二开写入、没有 `ccSwitchProviderId` 的 `models.json` 条目会被上游视为用户条目保留而不再接管，可能与新写入的同名模型冲突，需要用户在 WorkBuddy 中手动清理旧条目；本轮未在真实数据上验证。
- 曾通过设置页覆盖 WorkBuddy 目录的用户，覆盖值不再生效（未删除，只是不再读取），需改用 `WORKBUDDY_CONFIG_DIR`。
- 回退：本轮没有改动 `ccs-dev`，弃用新分支即可。若将来基于新分支发布并升级了数据库，旧版本不能读取 schema 26，需使用升级前的数据库备份。
